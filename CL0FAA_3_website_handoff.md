# Website dev brief: canonical order number everywhere (CL0FAA §3)

## Context

The CEO's brief (`CL0FAA_1.MD`, Aug 27 2026) asked for **one order number, shown identically everywhere** — internal portal, customer portal, invoices, emails, URLs, tawk.to. §1 (invoice numbering) and §2 (auto PAID-invoice email) are done on the CRM side. **§3 is the part that needs your side of the codebase** — the CRM repo (Vite/React, `portal.pandapatches.com`) can't touch it because the customer portal (`login.pandapatches.com`) is a separate Next.js/Sanity codebase.

**Why this matters (the actual trigger):** the CEO watches tawk.to's live-visitor view, which shows the URL a customer is currently on. Right now it shows a short number like `1149`, which doesn't match anything support can search for in the CRM — the CRM only knows orders by `PP-11248`. Support can't identify who's live-chatting.

## The canonical identifier

**`orders.order_number`** (format `PP-11248`) is the single source of truth. It's generated by a Postgres trigger + sequence on insert, immutable once assigned, and it's what the CRM, invoices, and all outbound emails already use. Read it straight from the shared Supabase Postgres project (`uxgzlneefybifvccfhwp`) — same backend the CRM uses, `orders` table, column `order_number` (text).

**What you're very likely using today instead:** `orders.id` — the raw bigint primary key. That's almost certainly where `1149` is coming from. Please confirm this on your side (check whatever variable populates your `/customer/order/:x`-style route), but it's the only other numeric identifier that exists on this table and matches the "short number" the CEO described.

## What to change

### 1. Display
Everywhere the customer portal shows an order number — dashboard, order detail page, order history list, any confirmation screens you render — read `orders.order_number` and show it as-is (`PP-11248`). Stop using `orders.id` for anything customer-visible.

### 2. URLs
Change your order-detail route from whatever raw-`id` pattern it uses today to the canonical number, e.g. `/customer/order/PP-11248` instead of `/customer/order/1149`.

**Important:** the CRM already assumes this. `src/services/orderService.ts` builds links into your site as `https://login.pandapatches.com/customer/order/${order.orderNumber}` (already `PP-11248` format) when it emails customers — same in `supabase/functions/notify-order-message/index.ts`. If your route currently expects a raw numeric id, those CRM-generated links may already be silently broken (404 or wrong order). Please verify.

### 3. Old-URL redirects
Add a 301 from the old numeric-id path to the new canonical one (Next.js `redirects()` in `next.config.js`, or middleware) — look the order up by `id`, redirect to `/customer/order/{order_number}`. Old bookmarks and old emails still need to resolve.

### 4. Page titles (do this one first — cheapest, most immediate payoff)
Set `<title>` on the order/dashboard pages to something like `"Order PP-11248 — Panda Patches"` (`next/head` or `generateMetadata`, depending on which router you're on). tawk.to shows the page title alongside the URL — this alone makes a live-chat visitor identifiable even before #2/#3 ship.

### 5. Backfill `legacy_customer_ref`
The CRM side just added `orders.legacy_customer_ref` (nullable text, already indexed) — a place to preserve whatever number a customer's old emails/bookmarks reference, so a support agent can still find the order if a customer quotes an old number. **You're the one who knows the old numbering scheme** (whatever `id`-based or other scheme the portal used historically) — please run a one-time script that writes the old customer-facing value into `legacy_customer_ref` for every existing order (keyed by `id`, since that's presumably the join key you have). The CRM's internal search already matches on this column — nothing further needed from CRM once it's populated.

*(Side note, only if useful context: there's evidence the customer portal used to live inside the CRM repo itself, under `portal.pandapatches.com/customer/*`, before moving to your site — `docs/customer-journey.md` in the CRM repo still describes that old setup. If your numbering scheme predates the move, that's probably where it came from.)*

## Edge cases / out of scope

- **Net-30/manual invoices** (schools, POs) — unaffected, not customer-portal-facing.
- **Refunds/cancelled orders** — no special handling needed here, same identifier rules apply.
- **Numbering never resets, no gaps required** — don't try to make `order_number` sequential-looking from the customer's perspective; it already skips around from voided forms, which is fine.
- Do **not** rename or renumber any historical order — `legacy_customer_ref` exists specifically so nothing has to change from the customer's side, they just get an additional canonical identifier going forward.
